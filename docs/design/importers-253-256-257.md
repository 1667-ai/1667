# Importers and terminal-safe text — design for issues 253, 256, and 257

This document is a design. It does not change code.

## Technical Names

Use these terms with one meaning each.

- **Archive** — a NovelAI `.story`, `.scenario`, or `.lorebook` file.
- **Container** — the `.story` archive, which holds prose and settings together.
- **Lorebook** — the entry collection inside an archive, or a `.lorebook` file.
- **Lorebook Entry** — one record in a Lorebook.
- **Entry Mapping** — the one function that turns a Lorebook Entry into a Fact.
- **Memory** — NovelAI's persistent free-form block.
- **Author's Note** — NovelAI's near-generation instruction block, and the 1667
  per-story field that #247 shipped.
- **Fidelity Report** — the account of what an import or an export changed or
  omitted.
- **Terminal Projection** — the display-only map from stored text to drawn text.
- **Control Mark** — the glyph that shows where a control character was.

## What this design delivers

| Issue | Delivery |
| --- | --- |
| 253 | One Terminal Projection at one choke point. Stored text stays exact. |
| 256 | `.lorebook` import into an existing story. `.scenario` import as a new story. |
| 257 | Full `.story` Container import: Lorebook, Memory, and Author's Note. |

Issues 256 and 257 share one Entry Mapping. It exists once, in
`shared/novelai-lorebook.ts`.

# Part 1 · Issue 253 — the Terminal Projection

## 1.1 The decision

**Use a display-only Terminal Projection. Do not refuse control characters at
the import boundary.**

The Terminal Projection is:

- **total** — it runs on every string the TUI draws, without exception;
- **length-preserving** — one UTF-16 code unit maps to exactly one UTF-16 code
  unit;
- **width-preserving** — the replacement has the same cell width as the source
  under `tui/src/cell-width.ts:54` `graphemeWidth`;
- **applied at one choke point** — `frameStyledText` and `frameText` in
  `tui/src/screens/story/frame.ts`.

Stored text stays byte-exact. Importers count control characters and name the
count in the Fidelity Report. Importers do not remove them and do not refuse
the file.

## 1.2 Why not refuse at the import boundary

Refusal fails on five counts.

1. It does not fix a story that is already on disk. The reading column would
   still draw an escape sequence from a story imported last week.
2. Import is not the only way text enters a story. The HTTP API `createFact`
   accepts text. The `$EDITOR` handoff accepts text. The composer accepts
   pasted text, and a terminal paste can carry control bytes. A model response
   can carry control bytes. None of these paths is an importer.
3. A whole manuscript is refused for one stray byte. The writer cannot easily
   repair a MessagePack Document or a PNG chunk.
4. It changes what the product accepts. That needs a product decision, and it
   buys no safety while (1) and (2) hold.
5. The display path must be correct anyway. Once it is correct, refusal adds
   nothing except lost work.

The Terminal Projection fixes every surface at once, fixes stories that already
exist, and keeps the writer's file faithful. It is the only fix that is
retroactive.

## 1.3 Why length preservation is the load-bearing property

The issue warns that a projection which changes string length must run before
measurement. This design removes that hazard instead of managing it.

Every character in scope is a single BMP code unit. Every replacement is a
single BMP code unit of the same cell width. Therefore:

- `String.prototype.length` is unchanged;
- every index into the string is unchanged;
- `visibleWidth`, `truncate`, `truncateTail`, `fitLine`, `padCells`,
  `sliceLine`, and `splitLine` (`tui/src/screens/story/frame.ts`) return the
  same values;
- `wrapText` and `createResumableWrap` (`tui/src/wrap.ts:99,130`) produce the
  same bounds;
- the wrap cache identity `WrapContentIdentity.textLength`
  (`tui/src/wrap.ts:31`) still matches, so the projection cannot cause a cache
  miss or a stale hit;
- the style runs that `storyPartWrapPlan` builds from `part.humanSpans` and the
  streaming offset (`tui/src/screens/story/row-layout.ts:373`) still land on
  the same characters;
- `FrameSegment.storySource.start` (`tui/src/screens/story/frame.ts:32`) still
  maps a drawn cell back to the correct source offset, so terminal selection
  and the human-edit attribution stay correct;
- every golden frame keeps its columns.

Because of this, the projection is safe **after** measurement. That is what lets
the choke point sit at the last possible moment, where nothing can bypass it.

A projection that deleted characters, or that collapsed a run of control
characters into one marker, would break every item in that list. This design
rejects both.

## 1.4 The character table

Two regimes. **Line** is the default. **Prose** is the opt-in for text that a
wrapper lays out.

| Code points | Name | Prose | Line | Reason |
| --- | --- | --- | --- | --- |
| U+0000–U+0008 | C0 | `▪` | `▪` | The terminal acts on them. |
| U+0009 | TAB | keep | keep | Legitimate. `graphemeWidth` already gives it width 2, and OpenTUI draws it as two cells. |
| U+000A | LF | keep | `▪` | The wrap layer owns LF. A single-row field must never hold one. |
| U+000B–U+000C | VT, FF | `▪` | `▪` | They move the cursor. |
| U+000D | CR | space | space | A lone CR returns the cursor to column 0 and lets a file overwrite the row. A space is the honest reading and adds no noise to text that came from Windows. |
| U+000E–U+001F | C0, includes ESC | `▪` | `▪` | ESC starts every escape sequence. This is the reported defect. |
| U+007F | DEL | `▪` | `▪` | Control. |
| U+0080–U+009F | C1, includes CSI | `▪` | `▪` | Some terminals act on them. `plainTerminalText` already removes them. |
| U+2028, U+2029 | Line and paragraph separator | `▪` | `▪` | In scope. `wrapText` does not break on them, so they sit inside a row, and some consumers do break on them. `shared/fact-activation.ts` and `shared/character-card.ts` already treat them as line breaks, so one rule now holds everywhere. |
| U+202A–U+202E, U+2066–U+2069 | Bidi embedding, override, isolate | keep | `▪` | In scope for the Line regime only. They reverse a run of pure ASCII, which is the file-name spoof. In prose they are how right-to-left text is written, so removing them there would be a real regression. |
| U+200E, U+200F | LRM, RLM | keep | keep | Out of scope. They only steer neutral characters between strong characters, so they cannot invert an ASCII name. Named as accepted residual risk. |
| U+200B, U+200C, U+200D, U+FEFF | Zero-width | keep | keep | Out of scope. They cannot drive a terminal. U+200D joins grapheme clusters, so marking it would split clusters and change measured width — the exact failure this design exists to prevent. |

**Zero-width characters carry a separate, pre-existing defect.** `graphemeWidth`
returns 1 for U+200B and U+FEFF, and a terminal draws 0 cells. That is a column
drift bug in the width model, not a control-character bug. Record it as its own
issue. Do not fold it into this work, because fixing it changes measured width
and therefore changes every wrap.

**Which regime a surface gets is not a caller decision.** Add one optional flag
to `FrameSegment`:

```ts
/** This segment is prose a wrapper laid out. Bidi controls and LF survive. */
prose?: true;
```

The default is the strict Line regime. A new surface that forgets the flag gets
the safe behaviour. Only three places set it: the reading column
(`row-layout.ts`), the expanded Fact body in the Facts rail
(`facts-rail.ts:55`), and the composer.

## 1.5 The choke point

`frameStyledText` (`tui/src/screens/story/frame.ts:74`) is the only function
that turns `FrameLine[]` into the `StyledText` the renderer paints. It has two
callers: `tui/src/app.ts:153` and `tui/src/story-surface.ts:139,160,166,172,175`.
`frameText` (`:68`) is the same output for `--render-once` and for golden frame
tests.

Apply the projection there, to segment text only:

- in `frameStyledText`, project `part.text` at the `append(part.text, …)` call;
  the `"\n"` the function appends between lines is app chrome, so it is never
  projected;
- in `frameText`, project each line before the join, for the same reason.

`plainLine` stays raw. It is a measurement helper
(`tui/src/screens/story/status.ts:87,89,123,126,129,159`), and measuring raw
text is correct exactly because the projection preserves width. Add a test that
asserts `visibleWidth(project(s)) === visibleWidth(s)` and
`project(s).length === s.length` over the whole table, so the two can never
disagree.

**Alternatives rejected.**

- *Per-surface `plainTerminalText` calls*, which is what #259 did for the card
  panel. Forgettable. That is the defect issue 253 reports.
- *Inside the wrap layer*, applied as it iterates graphemes. `wrapText` is one
  consumer of many. The status bar, the keyline, the breadcrumb, every panel
  row, every toast, and every hint reach the terminal without ever calling
  `wrapText`. This would leave most of the app unprotected.
- *Inside `graphemeCells`*. It is a measurement function used by
  `truncate`, `sliceLine`, and `splitLine`, but the drawn string is assembled
  from `part.text` in `frameStyledText`, not from cells. It would not cover the
  draw.
- *In the service or storage layer*. It mutates stored text, and it cannot help
  a story that already exists.

## 1.6 What the writer sees

A **Control Mark**, one cell per control character, in the danger role. The
state matrix already gives invalid values the ember colour, and this text is
invalid.

The mark defangs the introducer and leaves the rest of the sequence as inert
printable text. That is the point: the writer can see what the file tried to do.

```
stored     the paper: <ESC>[2J<ESC>[H — do not walk the cliff road
drawn      the paper: ▪[2J▪[H — do not walk the cliff road
```

The mark is not the whole answer. A speck in the prose does not say where it
came from. The import boundary says that, once, in the Fidelity Report and in
the toast:

```
14 control characters in prose. They draw as ▪ and are kept in the file.
```

`▪` is not in `COMPONENTS.md`. See **Part 4 · Proposed library additions**.

## 1.7 The `plainTerminalText` question

`shared/terminal-text.ts` currently removes characters. That changes length,
which this design forbids inside the frame. Two behaviours for one job is a
drift risk.

Make `shared/terminal-text.ts` the single owner of the table and export the
projection, in both regimes, as the only behaviour:

```ts
export const CONTROL_MARK = "▪";
export function terminalLineText(value: string): string;   // strict, the default
export function terminalProseText(value: string): string;  // keeps LF and bidi
```

Delete `plainTerminalText`. Update its call sites:

- `tui/src/import-cli.ts:22,78,82`, `tui/src/card-import-cli.ts:30,70,76,97,104`,
  `tui/src/import-project.ts:26,33`, `tui/src/card-import.ts:44` — these write to
  standard output and standard error, which the frame does not own. They call
  `terminalLineText`. A marked control character in a redirected log is fine.
- `tui/src/screens/card-import-panel.ts:41,51,81` — remove the calls. The choke
  point covers the panel now, and a double pass is a second behaviour waiting to
  drift.

## 1.8 Out of scope, named

- The composer does not sanitise a paste. The projection makes the paste safe to
  draw, and the stored text keeps what the writer pasted. Whether a paste should
  be cleaned is a separate product question.
- `1667 export` writes stored text to a `.md` file exactly. The terminal is the
  boundary, not the file. Mangling a writer's manuscript on export would be
  worse than the defect.
- The zero-width width defect in §1.4.

## 1.9 Tests

Follow the project rule: end-to-end first.

| Type | Test |
| --- | --- |
| End-to-end | `1667 --render-once` over a fixture story whose part text holds ESC, BEL, CR, U+0000, U+009B, and U+202E. The frame holds `▪`, holds no byte below 0x20 except the frame's own newlines, and matches column for column a control-free fixture with `▪` written in place. |
| End-to-end | `1667 import <file.story>` where the Container title and prose hold control characters. Standard output holds no ESC. The story then opens and draws. |
| Integration | `frameStyledText` and `frameText` over a built `FrameLine[]` that mixes both regimes. |
| Integration | The projection over every row of the §1.4 table: length is equal, `visibleWidth` is equal. |
| Integration | A Fact whose text holds ESC, drawn in the Facts panel, in the Facts rail collapsed row, and in the Facts rail expanded body. |

# Part 2 · The Entry Mapping (shared by 256 and 257)

## 2.1 Where it lives

`shared/novelai-lorebook.ts`. This mirrors `shared/character-card.ts:47`
`factsFromCharacterCard`, which is the existing "file to Facts" precedent.

```ts
export const SUPPORTED_LOREBOOK_VERSION = 6;
export const MAX_LOREBOOK_JSON_BYTES = 1_000_000;

export interface LorebookImport {
  readonly facts: readonly FactInput[];
  readonly fidelity: readonly string[];
}

/** Turn a parsed Lorebook into Facts, bounded by the room the story has left. */
export function factsFromLorebook(value: unknown, room: number): LorebookImport;

/** Read a `.lorebook` file: JSON, or JSON inside a PNG text chunk. */
export function parseLorebookArchive(bytes: Uint8Array): unknown;
```

## 2.2 The mapping

This is the exact inversion of `server/novelai-export.ts:223` `lorebookEntry`.

| Lorebook Entry field | Fact field | Rule |
| --- | --- | --- |
| `enabled: false` | — | Skip the entry. A disabled entry is switched off in the source; importing it live would change what the model reads. Counted. |
| `text` | `text` | Trim. Normalise CR, CRLF, U+2028, and U+2029 to LF. Refuse an unpaired surrogate. Over 4,000 UTF-16 code units, cut at the last paragraph break, then line break, then word break at or before the cap, and never between surrogates. Counted. Empty after the trim: drop the entry, counted. |
| `displayName` | `tag` | Trim. Empty or absent: fall back to the category name. Still empty: `null`. Over 48 Unicode scalars: cut with `sliceUnicodeScalarPrefix`. Counted. |
| `category` | `tag` fallback | Resolve the id against `categories[].name`. The exporter writes `id = "category:" + tag` (`server/novelai-export.ts:206`), so a 1667 export round-trips. |
| `keys` | `keys` | Keep strings only. Trim. Drop an empty key. Drop a key that holds a comma or a line break, because `parseFactKeys` refuses both. Cut a key over 64 scalars. Drop a duplicate after normalisation. Keep the first 32. Every drop counted. |
| `forceActivation` | `activation` | `true` gives `"always"`. Anything else gives `"keyed"`. |
| `searchRange`, `keyRelative`, `nonStoryActivatable`, `contextConfig`, `loreBiasGroups`, `advancedConditions`, `lastUpdatedAt`, `id` | — | Not imported. Named once in the Fidelity Report. |

**A keyed entry with no usable keys is imported as `keyed` with no keys.** It
never activates. That is what the source said. Promoting it to `always` would
change what the model reads, so the report names it instead:

```
2 keyed entries have no keys and will not activate.
```

## 2.3 The 128-Fact ceiling

`server/story-facts.ts:27` `createFacts` refuses a whole batch that does not
fit. An import must not fail because the archive is generous.

`factsFromLorebook(value, room)` takes the room the story has
(`MAX_FACTS - story.facts.length`) and returns at most that many Facts, in
`entries` order. The exporter writes `order: []`, so `entries` order is the only
order there is. The report names the remainder:

```
41 entries read. 34 imported. 7 did not fit the 128-Fact limit.
```

**The request body limit can bite first.** `MAX_JSON_BODY_BYTES` is 1,000,000
bytes, and 128 Facts of 4,000 characters can exceed it. Reuse
`shared/character-card.ts:89` `factImportRequestBytes`. If the body is too
large, drop Facts from the end until it fits, and name the drop in the report.
This differs from `planCardImport`, which throws. A card is small enough for a
writer to shorten by hand; a 500-entry Lorebook is not.

## 2.4 The `parseText` asymmetry — call it out

`server/story-facts.ts:132` `parseTag` caps the tag with
`unicodeScalarLength(tag, MAX_FACT_TAG_CHARS)`, which counts Unicode scalars.
`:143` `parseText` caps the text with `value.length`, which counts UTF-16 code
units. The two limits are advertised with the same word, "character", and they
mean different things.

Consequence for this work: **the Entry Mapping must cut Fact text by UTF-16
code units.** A cut by scalar count would produce a 4,000-scalar Fact that
`createFacts` then refuses with a 400, and the import would fail after the
report already said the entry was truncated.

Record the asymmetry as its own defect. Do not fix it here: making `parseText`
scalar-based loosens a stored limit and changes the HTTP contract.

## 2.5 PNG-embedded Lorebooks

Factor the PNG chunk walk out of `shared/character-card.ts:93` `parsePngCard`
into `shared/png-text-chunk.ts`:

```ts
export function readPngTextChunk(bytes: Uint8Array, keyword: string): string | null;
```

It keeps every rule the card path already enforces: reject a truncated chunk,
reject an invalid chunk length, reject compressed `zTXt` and `iTXt`
(`:119`), require ASCII metadata (`:302`), require `IEND` (`:131`), reject a
duplicate keyword (`:113`), and reject invalid or oversized Base64 (`:266`).
`parseCharacterCard` and `parseLorebookArchive` then share one implementation,
which is the same "it should exist once" rule the issues ask for.

**Implementation check.** NovelAI writes the Lorebook JSON into a `tEXt` chunk
under the keyword `naidata`. Confirm the keyword against a real NovelAI Lorebook
PNG before the parser is written. An unknown keyword must produce a named
error, not a silent empty import:

```
no lorebook data in this PNG · export the lorebook again from NovelAI
```

## 2.6 Shared budgets

Every import path keeps the budgets that already exist. Nothing new is
introduced.

| Budget | Value | Source |
| --- | --- | --- |
| File size | 20 MB | `MAX_IMPORT_BYTES`, enforced by `tui/src/import-file.ts` `readImportBytes` with `O_NOFOLLOW`, `O_NONBLOCK`, an `isFile()` check, and a size-change guard |
| Lorebook JSON | 1 MB | `MAX_LOREBOOK_JSON_BYTES`, mirroring `MAX_CHARACTER_CARD_JSON_BYTES` |
| JSON values | `MAX_NOVELAI_JSON_VALUES` | `server/import-nai.ts:24`, via `parseJsonRejectingDuplicateKeys` |
| MessagePack | records, tokens, depth, scalar bytes | `server/import-nai-msgpack-preflight.ts:25` |
| Facts | 128 | `MAX_FACTS` |
| Fact text | 4,000 UTF-16 code units | `MAX_FACT_TEXT_CHARS` |
| Fact tag | 48 Unicode scalars | `MAX_FACT_TAG_CHARS` |
| Fact keys | 32 keys, 64 scalars each | `MAX_FACT_KEYS`, `MAX_FACT_KEY_SCALARS` |
| Author's Note | 4,000 | `MAX_AUTHORS_NOTE_CHARS` |
| Parts and characters | 5,000 and 4,000,000 | `MAX_PARTS`, `MAX_TOTAL_CHARS` |
| Title | 4,096 | `MAX_STORED_TITLE_CHARS` |
| Request body | 1 MB | `MAX_JSON_BODY_BYTES` |

# Part 3 · Issues 256 and 257 — the importers

## 3.1 Which command does what

One rule, stated once in `HELP`:

> `import` makes a story. `import-card` and `import-lorebook` add Facts to a
> story that already exists.

| Command | Accepts | Result |
| --- | --- | --- |
| `1667 import` | `.md`, `.jsonl`, `.story`, `.scenario` | One new story per file |
| `1667 import-card --story <id-or-title>` | V1 and V2 JSON and PNG cards | Facts in the named story |
| `1667 import-lorebook --story <id-or-title>` | `.lorebook` JSON and PNG | Facts in the named story |

`--story` is required for `import-lorebook`, exactly as `card-import-cli.ts:35`
requires it. Reuse `selectStory` (`:87`) and `oneStoryTitleMatch` (`:104`)
without change.

**A wrong verb names the right one.** This is the C-27 rule applied to the
command line.

```
$ 1667 import lantern.lorebook
lantern.lorebook: a .lorebook adds Facts to a story that already exists —
  use: 1667 import-lorebook --story <id-or-title> lantern.lorebook

$ 1667 import-lorebook --story lantern lantern.story
lantern.story: a .story makes a new story — use: 1667 import lantern.story
```

**Rejected: one `import` verb with an optional `--story`.** It makes `--story`
sometimes required and sometimes forbidden, and it lets
`1667 import a.md b.lorebook` half-create and half-attach.

## 3.2 `.scenario` — a new story primed from the template

`server/import-scenario.ts`, `partsFromNovelAiScenario(jsonText)`.

| Scenario field | Result |
| --- | --- |
| `scenarioVersion` | Must be 3. Anything else is refused by name, matching how `import-nai.ts:49` refuses an unknown `storyContainerVersion`. |
| `title` | Story title, through the same normalisation as `import-nai.ts:70` `importTitle`: NFC, line breaks to spaces, `MAX_STORED_TITLE_CHARS`, refuse an unpaired surrogate. |
| `prompt` | Story parts. Split on blank lines, the same rule `partsFromMarkdown` uses for prose blocks. A new `partsFromProse(text)` does this without Markdown's heading rules, because a `#` in a NovelAI prompt is prose. |
| `context[0].text` | Memory. One Fact tagged `memory`. See §3.4. |
| `context[1].text` | The story's Author's Note. See §3.3. |
| `lorebook` | Facts, through the Entry Mapping. |
| `description` | Not imported. It is catalogue text, not steering text. Named in the report. |
| `placeholders` | The `${…}` tokens stay in the text exactly as written. The `placeholders` array of defaults and descriptions is not imported. Both named in the report. |
| `tags` | Not imported. A 1667 story tag marks a line, which is a different concept. Named in the report. |
| `ephemeralContext`, `storyContextConfig`, `settings`, `contextDefaults`, `phraseBiasGroups`, `bannedSequenceGroups`, `messageSettings`, `userScripts`, `author` | Not imported. Named in the report. |

**An empty `prompt` gives a story with zero parts.** A scenario can be pure
Lorebook and Memory, and that is a legitimate primed story. `storyFromImport`
already handles an empty part list with `activeRootId: null`. The report says
`0 prose parts`.

## 3.3 `context[1]` becomes the Author's Note, not a `rules` Fact

Issue 256 proposes that the instruction block "lands as a `rules`-tagged fact
until a per-story brief exists". #247 shipped the per-story Author's Note, so
that condition is met.

`context[1]` **is** the Author's Note in a NovelAI archive. The exporter writes
it at `budgetPriority -400`, `reservedTokens 1`, `insertionPosition -4`
(`server/novelai-export.ts:128`), which is NovelAI's Author's Note position.
The cap matches: `MAX_AUTHORS_NOTE_CHARS` is 4,000.

Mapping it to a `rules` Fact would make `.scenario` and `.story` disagree about
the same NovelAI field. That is the exact split issue 253 objects to. Map it to
the Author's Note in both.

**Round-trip asymmetry, named.** `.scenario` export puts the *global* author
brief (`settings.effective.systemPrompt`) into `context[1]`, not the story's
Author's Note. So 1667 → NovelAI → 1667 turns a global brief into a per-story
note.

**Recommendation, in scope with this work:** change `scenarioArchive` to write
`story.authorsNote` into `context[1]`, and name the author brief as omitted in
the export Fidelity Report. The field then means one thing in both directions.

## 3.4 Memory becomes one Fact

One Fact: `{ tag: "memory", text: <the whole block>, activation: "always",
keys: [] }`.

NovelAI's Memory is durable background — premise, setting, point of view —
pinned near the top of every request. A 1667 Fact with `always` activation is
that same surface. Splitting the block into paragraphs would invent structure
the source never had, and it would spend several of the 128 Facts on one idea.

Over 4,000 UTF-16 code units: cut at the last paragraph break at or before the
cap, and report it.

Order matters against the ceiling. Import the Memory Fact first, then the
Lorebook Entries in archive order.

## 3.5 `.story` — the full Container

`server/import-nai.ts:26` `partsFromNovelAiStory` currently reads only
`storyContainerVersion`, `metadata.title`, `content.document`, and the legacy
`content.story.fragments[].data`. Widen its result:

```ts
export interface NovelAiContainerImport {
  readonly story: GenericImport;          // title and parts, unchanged
  readonly facts: readonly FactInput[];   // Memory Fact, then Lorebook Facts
  readonly authorsNote: string | null;
  readonly fidelity: readonly string[];
}
```

| Container field | Result |
| --- | --- |
| `content.lorebook` | Facts, through the Entry Mapping. |
| `content.context[0].text` | Memory Fact. §3.4. |
| `content.context[1].text` | Author's Note, through `normalizeAuthorsNote`. Over `MAX_AUTHORS_NOTE_CHARS`: truncate and report. |
| `content.settings`, `content.storyContextConfig`, `content.contextDefaults`, `content.ephemeralContext`, `content.phraseBiasGroups`, `content.bannedSequenceGroups`, `content.messageSettings`, `content.sideChats`, `content.userScripts`, `content.scriptStorage` | Not imported. Generation settings. |
| The Document's `history` | Not imported. Retry history. |

The documented omission list shrinks from five items to two headline items:
**generation settings** and **retry history**.

**The import is one atomic story write.** Build the `Story` with
`storyFromImport`, then call `createFacts` on it, then call `setAuthorsNote` on
it, then persist once. Do not create the story and patch it afterwards; a
failure would leave a half-imported story on disk. Calling `createFacts`
directly is also what keeps the import validated by the same `parseTag`,
`parseText`, and `parseFactKeys` the API uses. The importer trims to the
ceiling first, so `createFacts` never throws its 409.

**Protocol change.** `shared/worker-protocol.ts:170` `importNovelAI` output
becomes `{ payload: StoryPayload; fidelity: string[] }`. Add
`importScenario` and `importLorebook` beside it, in the same mutating-method
lists at `:187`, `:212`, `:217`, `:236`, and `:443`.

## 3.6 `.story` export drops Facts — a scope call-out

`server/novelai-export.ts:97` writes `content.lorebook = lorebookArchive([])`,
and `content.context = []`. A `.story` export therefore carries no Facts, no
Memory, and no Author's Note, while `.story` import will read all three.

The round trip does not close. This is not required by 256 or 257.

**Recommendation:** make `storyArchive` write `lorebookArchive(story.facts)`
and a `context` pair holding the Memory Fact's text and the Author's Note, and
change the `.story` Fidelity Report accordingly. Do this in the same change set

# Part 5 · Proposed library additions

`COMPONENTS.md` says: if a feature needs something that is not in the list, add
it to the list first. This design needs one new part and one foundation
amendment. Nothing else in Parts 3 and 4 is new.

## C-38 · control mark

> **Use when** a stored string holds a character the terminal would act on, and
> the surface must show that something was there without letting it act.

```
glyph      ▪            one cell · ember · never repeated for a run

prose      the paper: ▪[2J▪[H — do not walk the cliff road
name       ~/nai/lantern▪gnp.txt
tag        memory▪rules
absent     the paper: [2J[H            ← what a strip would leave: a lie
```

- **One mark per character, never per run.** The mark exists inside a
  length-preserving projection; collapsing a run would move every column to its
  right and break wrapping, truncation, style runs, the wrap cache, and the
  selection map.
- **One cell.** U+25AA is not `Emoji_Presentation`, is not full-width under
  `tui/src/cell-width.ts:71` `isFullwidthCodePoint`, and is present in DejaVu
  Sans Mono, Menlo, and Cascadia Mono. It is a geometric block, which is the
  family the foundations already allow.
- **Ember.** The state matrix gives an invalid value the danger colour. This
  text is invalid.
- **It never appears alone.** The surface that produced the text also names the
  count, once, in a C-28 toast or a C-32 result line, with `!` to the C-37 log.
- **Degradation.** 80 columns: unchanged. 256-colour or no colour: unchanged —
  the shape carries it, which is why a solid speck was chosen over a colour
  change.

**Rejected: `·`.** It is already in the marks row and already means "separator"
in every hint, status bar, and keyline. One meaning per glyph forbids a second
job.

**Rejected: no mark, just a space.** A crafted file would then read as ordinary
prose with odd spacing, and the writer could never see what the file tried to
do.

**Rejected: the Control Pictures block (`␛`, `␀`).** It is neither box-drawing
nor a geometric block, and its coverage in the three named fonts is not
dependable.

## Foundation amendment — the marks row

Add `▪` to the marks row of the glyph table, with one meaning app-wide:

| Job | Glyphs |
| --- | --- |
| marks | `✓ · ✕ ⚑ ⟳ ▲ » › ‹ › ↵ ↑↓←→ ◈ ~ ▪` |

> `▪` always means "a character here is not text", never "a small bullet".
